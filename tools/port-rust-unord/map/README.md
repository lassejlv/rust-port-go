# Genuine partial UnordMap foundation

`datastructures.UnordMap` currently supplies concrete map construction,
lookup/mutation, standard Entry/TryInsert, ownership, derived Clone default
replacement, equality, and opaque borrowed read-items/filter-map collection.
It uses the real scoped Fx/SwissTable backing; no Go map stands in for it.

This is an explicitly partial foundation for the live span/DefId integration.
Generic iterator/sort/codec/stablehash APIs and whole-file source credit remain
pending. The narrow `CollectUnordMapFilterMap` callback is a static operation
witness with only trivial or borrowed captures; it does not pretend to support
unrepresented owned Fn environments.

The native driver links the complete unchanged `rustc_data_structures` crate
using `tools/port-rust-span-reference`'s frozen profile and complete link
arguments. Its expected values are not generated by reconstructing Unord from
selected method bodies. Default execution prepares/checks the shared reference
offline; `--skip-prepare` uses an already prepared cache and still verifies every
original source byte against its provenance.

```sh
python3 tools/port-rust-unord/map/generate.py --check
go test ./port/rust/compiler/rustc_data_structures/src \
  -run TestOriginalUnordMapFoundation -count=1
```

The2,000 original cases retain exact map results and bucket order across insert,
TryInsert, marking reads through GetMut, clone/default CloneFrom, removal,
clear, and the actual `.items().filter(...).map(...).collect()` result. Its lower
size hint is zero and output insertion follows input bucket order.

The proof uses `u64 -> (u64,bool)` with Rust pair layout24/8. Consumers must supply
their own exact Rust layout. In particular Span is packed to alignment4; its
tuple layouts must be measured from the original type rather than inferred from
Go's u64 alignment. Go pointer size is not a substitute for Rust layout metadata.
